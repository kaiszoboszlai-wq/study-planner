- **推定**：1時間当たりの定期処理の回数など。全利用者の実測値でも請求額の保証でもない。4〜10人という人数だけでは、原因ごとの実利用回数は確定できない。
- SDK呼び出し数と請求数は一致するとは限らない。空クエリの最低読取、集計クエリのインデックス読取、ルール内の `exists` 等、トランザクション再試行、SDKキャッシュを別途考慮する必要がある。

### 重複・監視・ループ・規模の確認

- Firestoreの `onSnapshot`／Realtime Databaseの `onValue` は見つからない。手動ポーリング方式。DMの4秒タイマーは `dmStop` で閉じる／会話切替時に解除され、非表示時も取得をスキップする。
- 再描画そのものが常に全データを取得するわけではない。ただし `renderFb` 等から一覧読取が呼ばれる経路はあり、従来は**個人データを書き込むたび閲覧キャッシュ全体を破棄**していた。短時間再利用が効きにくくなる原因だった。
- 更新による無限書込ループはコード調査と今回のテストでは確認していない。タイマー保存→公開保存、別の定期ハートビート、イベント由来の保存が重なる経路は確認した。
- 1人の操作が全登録ユーザーに書き込む処理は見つからない。ただし全員ランキングは、閲覧者1人ごとに当日の全N件を読むため、閲覧者が増えると積の規模になる。プロフィール変更の共有先更新は最大F件のファンアウトであり、全登録者への書込ではない。
- 入力は1キーごとに端末保存する場所があるが、クラウドは3秒／4秒のデバウンス。同じ値でも読取予約する無駄は改善。長い入力を途中で何度も止めれば複数回同期する性質は残る。

## 実装した改善

1. **全員ランキングを学習秒数降順の上位100件＋自分に制限**。全件走査を削除。上位外の自分には順位を捏造せず「上位100件外」を表示し、全登録者数も表示しない。単一フィールドのソートを使用し、スキーマ・ルール・複合インデックス追加は不要。
2. **タイマーの端末保存15秒は維持し、定期クラウド保存を60秒へ**。プロフィールと共有学習記録の変更判定を分離。記録が変わっただけではプロフィールを書き直さない。60秒の勉強中ハートビートは維持。同時公開要求も共有する。
3. **個人データが不変なら保存由来の読取を予約しない**。`syncPull` の同時実行を同じアカウント・認証世代で共有。通常の別端末定期確認は15秒から60秒へ。オンライン復帰・画面復帰時の確認は維持。
4. **無関係なキャッシュ破棄を抑止**。`privateData` の保存では公開プロフィール等のキャッシュを消さない。権限変更時の破棄、stats本体の毎回の認可確認は維持。
5. **プロフィール共有の無変更再配布を停止**。60秒ごとの強制処理を変更判定に置換。初回・プロフィール変更・フォロー操作・前回失敗は更新対象になる。
6. **コメント件数に集計クエリを使用**。件数表示だけのために本文全件をダウンロードしない。SDKに集計APIがない場合は従来処理へフォールバック。コメントを開けば本文を取得する。
7. **DMは更新情報を先に取得**。変化がなければメッセージ100件を再取得しない。更新時には即取得、取りこぼし防止として60秒ごとにも最新100件を再照合。送信側が会話情報を書いてから本文を書く間の競合では、本文到着を確認するまで次回取得を続ける。

`writeBatch` にまとめただけの削減は行っていない。不要なドキュメント書込・読取自体を減らした。

## 保存の安全性と同期への影響

- 計測済み時間の端末チェックポイントは15秒ごと。非表示・`pagehide`・`beforeunload` では端末保存を先に行い、未送信個人データの同期と公開更新を即時に試みる。
- ブラウザー強制終了時の非同期通信完了は保証できない。最後の端末チェックポイント以後の時間についても、OSによる強制終了では完全保証はできず、これは既存の制約。未送信の端末データ・タイマー開始情報・再送処理は残し、再起動時に利用する。端末ストレージ自体を消した場合には未送信分の復旧は保証できない。
- 読取失敗時にはクラウドを上書きせず、保存失敗を成功扱いにせず、既存の再送を維持する。停止時は個人記録保存が成功してからタイマーの端末間リースを解除する。
- 記録の加算・削除・プランの既存マージ、認証世代／UIDによる遅延応答の拒否、リースのトランザクションを維持。`privateData` はmerge保存でリースを保持する。
- 通常の別端末反映と公開学習時間の更新は、定期処理では最大約60秒＋通信時間となる。開始・停止・復帰等は別経路がある。DMの通常新着は従来の4秒周期で検知し、メタデータに現れない遅延・順不同送信は最大60秒＋通信時間で再照合する。

## 残っている課題

1. **本番の内訳確認**：検証専用Firebaseプロジェクトを分け、同一端末・同一操作・同一利用時間でConsoleの読取／書込を比較する。今回未デプロイなので、本番料金への効果はまだ発生しない。必要なら将来、個人情報を含まない経路別カウンターを開発時のみ有効にする。
2. **残る全件取得**：受信リクエスト、会話一覧、フォロワー一覧、開いた投稿のコメント／いいねは一部全件取得。承認・既読の仕様と整合するカーソルページング／件数集計へ段階的に移す余地がある。会話数Dが多い利用者の `dmCheck` は引き続きDに比例する。
3. **大規模ランキング**：今回は上位100件に仕様を明示。全員の正確な順位・総人数や上位外の全件閲覧が必要になれば、毎クライアント全件走査に戻さず、サーバー集計・ページングを別途設計する。同点が100件境界を跨ぐ場合は、表示対象を100件に制限する。
4. **個人データの大きさ**：`privateData` は引き続き1ドキュメントのスナップショット。1回1Wでも転送量・写真サイズ・1MiB制限・並行編集の複雑さは残る。公開ログは既存の120日分。レコード単位の分割は既存データ移行・ルール・複数端末の削除整合性まで含めた別作業が必要。
5. **100万人の試算**：登録者数だけでなくDAU、計測時間、ランキング閲覧頻度、フォロー数、DM頻度、リージョン／料金体系が必要。今回は金額や無料枠内を保証しない。フォロー先プロフィール変更のO(F)処理、クライアント発行できるクエリ上限のルールによる強制、日次データの保持期間も今後の検討対象。
6. **本番実機とオフライン**：今回のオフライン・失敗・競合はモックとローカルブラウザーで確認。本番SDKのオフラインキュー、ルール依存読取、複数の実機の強制終了、Firestoreエミュレーター／実プロジェクトによる料金相当の確認は未実施。
