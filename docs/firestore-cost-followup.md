## 2. 終了時の記録消失・復旧

「15秒ごとに保存する」ことは「どんな終了でも最大15秒しか失わない」という保証ではない。

| 操作・状態 | 失われ得る範囲 | 次回の復旧 |
| --- | --- | --- |
| 前面で動作中、保存成功、正常に非表示／ページ終了 | 終了イベントでその時刻までを端末保存する。端末保存成功まで確認できた分について計測時間の消失はない。クラウドへの送信完了は別 | 同じブラウザープロファイルの同じアカウントなら端末保存分を復旧。通信失敗でも端末データを再送する |
| 前面で定期処理が予定どおり動作中、終了イベントなしで強制終了、新しいタブで再開 | 通常は最後の15秒チェックポイント以後、**約15秒未満＋イベント処理遅延**。これは正常なスケジューリング条件での目安 | 最後に端末保存したログ・加算履歴・計測済み時間を復旧。別タブの認証済みタイマーは自動再開しない。未保存の末尾は自動復旧しない |
| バックグラウンド／画面ロックでブラウザーのJSが停止、その後OSが終了 | **最後に端末保存した時点から強制終了まで**。30分停止していれば約30分になり得る。OSの停止時間に上限がないため、コードだけで有限の最大秒数は保証できない | 停止前に保存できた記録は復旧。停止後の実際の勉強時間と、終了後の時間を区別する証拠がないので勝手に加算しない |
| 同じタブのリロード／セッション復元で `sessionStorage` のタイマーが残る | 開始時刻を引き継ぐため、その時刻からの経過を再構成できる。**リロード中・端末停止中も経過に含まれ得る** | 保存済みログに加え、同一タブのランタイムを復元。長く離れた場合は勉強時間として正しいか確認・調整が必要。OSがセッションを復元するかは環境依存 |
| 通信切断だけで端末保存は正常 | 記録を直ちに失うわけではない。クラウドとの差は切断中ずっと増える | 同じ端末で再接続・再ログインしたときに未送信分をマージして保存。別端末では未送信分がまだ見えない |
| 端末データ消去／プライベートモード終了／ブラウザー削除／別端末への乗換え | 最後に成功したクラウド保存以後の端末だけのデータ。前面・正常通信で定期保存だけなら通常約60秒＋4秒デバウンス＋通信時間が目安。オフライン・失敗・停止中は上限なし | クラウド保存分しか復旧できない。端末内だけの未送信分は復旧できない |
| localStorageの容量不足・書込拒否 | 最後に成功した端末保存以後。定期保存が全部失敗するなら上限なし | 成功済みの端末データ／クラウドデータまで。`store()` はエラーを保存状態に残す。今回の試験では容量不足実機は未検証 |

### 実施した復旧確認

- `timer-recovery.browser.cjs` ではChromiumの **`Page.crash`** でレンダラープロセスを終了し、終了イベントによるflushを通さず新しいタブを開いた。保存済み120秒が復旧し、未チェックポイントの約14秒相当の末尾は加算されず、古いタブのリースも再開しなかった。
- 復旧後に、記録が空の新しいクラウドスナップショットを適用しても、端末の未送信120秒が残ることを確認した。ログ・加算履歴の既存マージを使用している。
- 同じタブのリロードでは、開始時刻を含むランタイムが復旧し、120秒＋約14秒以上の経過を再構成することを確認した。リロード中も数えるという性質も確認した。
- 保存失敗後の再送、初回読取失敗時の上書き抑止、2端末加算・削除・プラン保持は既存の同期回帰テストで確認した。

これはローカルブラウザー／モックでの確認であり、iOSの実機強制終了、実Firebase SDKのオフラインキュー、ストレージ消去後の復旧を成功したとは扱わない。

## 3. 全件取得の棚卸しと追加改善

Rは返却ドキュメント数。集計クエリの課金は別途インデックスエントリ数に依存する。Q＝受信リクエスト、D＝会話、V＝フォロワー／閲覧許可、C＝投稿コメント。

| 優先度・経路 | 前回終了時に残っていた処理 | 今回の対応 | 残る制約 |
| --- | --- | --- | --- |
| 高：共通ヘッダー通知 | 15秒ごとQ＋D全件。元の60秒ポーリングも別関数として登録。共有プロフィールの強制処理も残存 | 最終ラッパーを修正。60秒の成功時刻制御・重複抑止、Qは件数集計、共有は変更判定。元のintervalも最新の `fbPoll` を呼ぶ形へ統一 | 通知は定期処理では最大約60秒＋通信時間の反映。操作後の明示更新は別 |
| 高：DM通知／会話情報 `fMem` | D件を呼出ごと取得 | アカウント別の60秒キャッシュと取得中の共有。自分の書込・認証変更時の破棄は維持 | **D件の全件取得自体は残る**。会話ごとに異なる `dmSeen` と比較して正確な未読会話数を出すため。新しい未読集計用データ構造にはスキーマ・ルール・移行設計が必要 |
| 高：マイページの人数／通知数 | `renderFb` ごとにV・Q本文を全部取得 | 既存の集計ヘルパーを再利用。フォロワー件数は従来どおり自分のUIDを除外 | 集計も無料ではない。ルール評価を含むDB実測は未実施 |
| 中：DM一覧の表示 | D人分のプロフィールを同時取得 | 既存の新着順を保ち、表示する50人ずつプロフィールを取得。「さらに50件表示」で続く | メタデータは上記D件。UIを50件にしただけでD件のサーバー読取が消えたとは扱わない |
| 中：受信リクエスト一覧 `fillReq` | Q件と全員のプロフィール | 50件ずつカーソル取得、続きボタン、失敗時カーソル保持・アカウント変更時の応答破棄 | ページ途中に追加された新規IDが前方に入る場合は明示再表示が必要 |
| 中：フォロワー一覧 `fillVie` | V件と全員のプロフィール | 同じく50件ずつ取得。閲覧許可解除・フォロー操作を維持 | 名前検索・並べ替えは読込済み範囲。画面にも明記。未取得の名前を横断検索するには別の索引設計が必要 |
| 中：コメント本文 `pxLoad` | C件と投稿者プロフィール | 50件ずつ取得。件数表示は集計、本文の削除・未送信再試行も維持 | 古いタイムスタンプ欠損データを落とさないよう、カーソルはドキュメントID順。読込済みの表示は日時順。未取得分を含む完全な日時順の先頭50件という意味ではない |
| 中：ログイン／関係変更のsocial公開配列 | V件全部を取得した後、200件に切り詰め | 最大201件だけ取得して自分を除外し、既存形式の最大200件を保存。全フォロワー数との長さの不一致による再保存を抑止 | 他人向けsocial配列の200件上限は従来仕様。自分の全フォロワー一覧は別のページ取得で利用可能 |
| 継続：フォロー中のプロフィール／共有記録 | フォローID最大100件に対して各人を取得 | 前回のキャッシュを維持。機密性のあるstats本体の再認可は省略しない | O(F)、最大100。これを削るために権限チェックを長期キャッシュしない |
| 互換分岐：集計APIがないSDK | `fCommentCount` のフォールバックが `fList` で全件 | 現行のFirebase 11.6.1には集計APIがあり、通常は集計分岐 | 古い／テスト用SDKでAPIを省くと全件フォールバックする。現行SDKを前提にした検証と区別 |

現行の実行経路で、コメント・リクエスト・フォロワーの本文全件取得は置き換え済み。未使用の古い関数やルール定義を、現在も実行される通信として数えない。Firestoreのリアルタイム購読を新たに追加していない。

## 4. ランキングの機能確認・補完

- 前回の100件制限には続き機能がなく、上位外の正確な順位も未実装だった。今回は「続きの100件を表示」を追加した。カーソルはSDKのDocumentSnapshotを使い、同点時にもドキュメントIDを含む順序で続きを指定する。重複クリックの並列取得を防止する。
- 「自分の順位を確認」は、自分の公開更新が成功した後で `seconds > 自分の秒数` の**集計件数＋1**を取得する。同点は同順位。60秒未満には従来どおり順位を付けない。上位外でも必要なときだけ確認でき、「確認時点」と明記する。
- 自分の順位を得るために他の利用者の本文全件を取得しない。ただし集計のインデックス読取には課金がある。100万件を集計する場合、一般的に最大約1,000読取単位相当が目安で、100万ドキュメント読取とは別。毎秒・自動再描画ごとの順位集計にはしていない。
- 205件の他人データ＋自分で、初回100件、続き100件、最後5件、重複クリック、ページ境界の同点100位・次の102位の表示、上位外の自分206位をブラウザーで確認。プロフィール・コメント・同点順位・320px表示などの既存テストも確認する。
- 初回の上位取得、続き取得、自己順位集計は別時刻のクエリ。ランキング更新中の原子的な全件スナップショットではない。途中でスコアが変われば、既読ページとの重複はUIDで抑えるが、移動して飛ばされた行は再表示で確認する。日付・認証・表示範囲の変更後の古い応答は適用しない。
- 正確な総参加者数は常時集計しない。周期更新時は先頭100件に戻るため、長く続きを閲覧する用途のUXは今後の改善余地がある。
