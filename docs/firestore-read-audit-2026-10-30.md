# Firestore読み取り調査と修正（2026-10-30）

対象は `kaiszoboszlai-wq/study-planner` の `1ad28a6f90a17ef3fad799fddcc62be45b3ecb8c`。取得した公開URLのHTMLは、このコミットのindex.htmlと差分なし。公開設定のプロジェクトは `study-planner-d2ee7`。本番Firestoreの使用量・課金・ユーザー別操作履歴にはアクセスしていない。報告された約11,000読み取り/日、約1,200書き込み/日はユーザー提供の概数であり、当日の集計完了は未確認。

## 原因の確認

| 処理 | 公開コードの動作 | 影響 |
| --- | --- | --- |
| 通知 | `assets/header-notifications.js` が `fbPoll` と `dmCheck` を上書き。前面タブでは毎分リクエスト件数と自分が参加するDM会話のメタデータを全件取得 | 操作しなくても継続。D会話なら概ね毎回 `max(D,1)` ドキュメント＋集計の読み取り。会話本文はここでは取得しない |
| 個人同期 | 前面タブでは毎分 `syncRefresh` → `syncPull` → `privateData/{uid}` をサーバーから確認 | タイマー・入力・ダイアログ等による抑止条件を除き、操作しなくても継続 |
| DM画面 | 開いている会話を4秒間隔で確認。メタデータを読み、既読は5秒キャッシュ。メタデータ不変でも1分ごとに直近最大100本文を取得 | メッセージが100件あれば、本文だけでも毎時約6,000件相当になり得る。実測ではなくコード上の推定 |
| ランキング | 世界ランキングは先頭100件＋必要時の追加ページ。フォローランキングはフォロー一覧、各プロフィール・学習記録などを取得。コメント数の集計もある | 見ている人数・フォロー人数に比例。`stats/{uid}` の権限確認は毎回行う設計 |
| ランキング表示判定 | 画面を「今日」のタブへ移した後も `state.page===8` を判定し、実際の「今日」は6 | 最新版では表示中の取得を誤って止める可能性がある。隠れたランキングを大量取得しているという結論ではない |
| リアルタイム購読 | 調査したindex.html・assetsにはFirestoreの `onSnapshot` 呼び出しなし | 主な継続取得はポーリング。認証状態の監視とFirestoreのデータ購読は別 |
| バックグラウンド | 主な定期読み取りに `document.hidden` の抑止あり | 非表示タブと、前面のまま放置したタブを区別する必要がある |

通知用の60秒タイマーはindex.htmlと追加スクリプトの両方にあるが、追加スクリプトの同時実行・59秒キャッシュで重複を抑制している。単純に2倍とは数えない。

## 修正

1. 最後のクリック・キー入力・ホイール・タッチから5分で、自動の通知取得、個人同期確認、DM確認、ランキング更新を停止。操作の再開時に更新。タブへ戻ったときも通常の更新を行う。
2. 通知の追加スクリプト側にも同じ停止条件を適用。未読数は手元の既読情報から更新でき、通知画面を明示的に開いたときは最新情報を取得する。
3. DMは新着メタデータが変わったら、手元の最新メッセージ時刻以降だけを取得。同一ミリ秒のメッセージを除外しないよう `at >= 最新時刻` とする。最大100件の再確認は1分から5分へ変更。
4. DMメタデータが本文より先に書かれる競合への再試行、既読表示、送信再試行、以前のメッセージのページ取得、アカウント切替の確認を維持。
5. ランキングの取得条件を実際の表示状態に変更。非表示の「今日」内タブでは取得せず、ランキング表示中は取得できる。

**動作の変更点**：5分放置後は、新着通知・相手のDM・別端末の編集・ランキングを自動表示しない。操作の再開またはタブ復帰で取得する。タイマーの記録保存、保存前の競合確認、通信回復後の保存再試行は停止しない。そのため「放置ユーザーの全Firestore読み取りが必ずゼロ」という保証ではない。停止前に始まった通信も完了し得る。

ランキングは表示判定の修復によって、以前は動かなかった表示中の取得が動く場合がある。この修復を読取回数の削減として計上しない。

## 効果の目安（推定）

- 操作・保存なしで1時間前面放置した場合、通知の定期クエリと個人同期確認は、初回込みでそれぞれ約61回から最大約6回へ減る。起動時刻とタイマーの位相による。1回当たりの読取件数は別。
- 操作を続けながら新着のないDMを1時間見ている場合、100件本文の定期再取得は約60回から約12回へ。メタデータ・既読の確認分と初回分は残る。100件の再取得に比べ、新着時は通常直近の少数メッセージだけを取得する。
- 25〜30人の登録・ログイン経験だけでは日次読み取り数を算出できない。前面で開いている時間、会話数、DM閲覧時間、フォロー人数、ルール評価、管理画面からの操作が必要。

1分ごとの100件DM再取得が長時間続けば、少人数でも11,000回に達する規模である。ただし今回の11,000回の主因と断定するログはない。

## 検証

- 単体テスト45件成功：firestore-idle、firestore-cost、firestore-followup、sync、record-sync、plan-sync、delete-record-timer。
- ブラウザーテスト3本成功：firestore-idle、firestore-cost、ranking-health。WindowsのEdgeをPlaywrightから使用し、通信境界をモック化。
- idleブラウザー検証は実際のページが登録する定期コールバックを60回呼び、放置後の通知・同期・DM読み取りが起動しないこと、操作1回で更新が再開することを確認。実時間1時間の実測ではない。
- DM新着表示、既存本文保持、過去ページ、ランキング先頭100件と続き、自分の順位、同点、プロフィール・コメントの既存ブラウザー検証も成功。
- `today-notifications.browser.cjs` は現行お知らせに対する古いゼロ件期待値で失敗。お知らせを除外して進めても320px幅のはみ出し期待値で失敗した。修正範囲外のため元のテストは変更していない。全テスト成功とは報告しない。
- 本番Firestoreの課金計測、実ユーザー認証での結合テスト、iOS実機検証は未実施。ローカルの変更であり本番には未反映。

## 実測手順

既存の `docs/firestore-real-measurement.md` と `tools/firestore-observe.js` を利用する。

1. 同じデータを持つ隔離検証プロジェクトで、変更前後を同じ操作・時間で比較。
2. 前面のまま1時間放置、非表示で1時間放置、操作を続けるDM（新着なし／あり）、ランキング表示、画面往復をそれぞれ別セッションで測る。
3. SDK観測器で呼び出し数・返却ドキュメント数を記録。空クエリ、集計、ルール評価、インデックス読み取り、キャッシュの扱いは別途確認。
4. Firebase使用量画面の対応時間帯と照合する。集計完了前の当日値を前日全体と直接比較しない。検証中に他の端末・管理画面から読まない。
5. 本番反映後は完了した同じ長さの期間で、利用時間・人数・操作を添えて比較する。

Firestoreは空クエリにも最低読取課金があり、セキュリティルールの `exists()` 等も追加読取になり得る。SDKの返却件数は請求数そのものではない。
